# Ambient Agent

## 定義

ユーザーの会話トリガーではなく、外部イベント・スケジュール・監視条件などをきっかけにバックグラウンドで自律的に動作するエージェント。必要な瞬間だけ人間の判断や承認を求める「アイドル→ピンポイント介入」の設計が特徴。

## 背景

従来のLLMインターフェースはユーザーがメッセージを送るたびにエージェントが応答するチャット型が中心だった。しかし実世界のタスクの多くは「特定のイベントが起きたときに自律処理し、判断が必要なときだけ人間に報告する」という形で機能する。メール処理・CI監視・定期レポート生成などのユースケースでは、チャット型よりもAmbient型のアーキテクチャが自然なモデルとなる。

## 詳細

### チャット型エージェントとの対比

| 観点 | チャット型 | Ambient型 |
|---|---|---|
| 起動トリガー | ユーザーのメッセージ | 外部イベント・スケジュール |
| ユーザーの存在 | 常に会話に参加 | デフォルトは非参加 |
| 質問・確認の方法 | 通常メッセージを返す | 構造化された介入イベント（AskUserQuestion等） |
| human-in-the-loopの位置づけ | デフォルト（毎ターン） | 例外（条件を満たした時のみ） |

### イベント駆動のhuman-in-the-loop

Ambient Agentが人間の判断を必要とする場面では、以下のフローが機能する：

1. バックグラウンドでAgentが処理を進める
2. 「ここだけ人間の判断が必要」という条件を検出
3. [[ask-user-question]]を呼び出して「ユーザーへのアクション要求」を構造化されたイベントとして発行
4. アプリ側がイベントを検知してプッシュ通知・メール・バッジ等でユーザーに通知
5. ユーザーがUIで回答すると、その回答だけをイベントとしてエージェントの続きに渡す

このフローにより、バックグラウンド処理とUI/通知レイヤーが疎結合になる。

### ハーネス設計への含意

Ambient Agentのハーネス設計では、チャット型と異なる考慮が必要になる：

- **非同期の状態管理**: エージェントが中断・再開できる永続化レイヤーが必要
- **通知インフラとの統合**: AskUserQuestion等のイベントを検知してユーザーに届ける仕組み
- **タイムアウト・キャンセル処理**: ユーザーが応答しない場合のデフォルト挙動
- **可観測性**: バックグラウンド処理の状態をトレースできる仕組み（[[trace-analysis]]参照）
