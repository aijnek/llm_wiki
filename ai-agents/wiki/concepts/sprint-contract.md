# スプリントコントラクト（Sprint Contract）

## 定義

コーディングタスクの各スプリント（実装単位）の開始前に、ジェネレーターエージェントとエバリュエーターエージェントが「完了の定義（Definition of Done）」と「検証基準」を事前に合意する仕組み。

## 背景

プロダクト仕様は意図的に高レベルに保たれることが多く、ユーザーストーリーと実際にテスト可能な実装の間にギャップが生じる。スプリントコントラクトはそのギャップを埋めるためのステップ。Anthropicの3エージェントハーネス（プランナー・ジェネレーター・エバリュエーター）の中で採用されたアプローチ。

## 詳細

### プロセス

1. **ジェネレーターが提案**：何を実装するか、どのように成功を検証するかを提案
2. **エバリュエーターがレビュー**：ジェネレーターが正しいものを作ろうとしているかを確認
3. **反復**：合意に至るまでファイルを通じてやりとり（ジェネレーターがファイルに書き込み → エバリュエーターが読んで返答 → 繰り返し）
4. **実装開始**：合意後、ジェネレーターが合意したコントラクトに基づき実装

### なぜファイル経由で通信するか

Claude Agent SDKでのマルチエージェント実装では、エージェント間の通信はファイルを介して行われる：
- ジェネレーターがファイルに書き込む
- エバリュエーターがそのファイルを読んで、同ファイルか別ファイルに返答
- 前のエージェントが返答ファイルを読む

これにより、実装の詳細を早期に過剰仕様化せず、必要な粒度の合意だけを事前に取ることができる。

### 具体例

Anthropicの実験では、Sprint 3だけで27の評価基準がコントラクトに含まれていた。エバリュエーターの発見が具体的で行動可能な形になっている例：

| コントラクト基準 | エバリュエーターの発見 |
|----------------|----------------------|
| 矩形塗りつぶしツールでクリックドラッグして選択範囲を塗りつぶせる | FAIL — ドラッグ開始・終了点にのみタイルが配置される。`fillRectangle`関数は存在するが`mouseUp`で正しく呼ばれていない |
| エンティティのスポーン位置を選択して削除できる | FAIL — `LevelEditor.tsx:892`のDeleteキーハンドラーが`selection`と`selectedEntityId`の両方を要求するが、エンティティクリックでは`selectedEntityId`のみセットされる |

### 制限と撤廃

Opus 4.6にアップグレードした際、スプリント構造自体が不要になった（[[context-anxiety]]が改善されたため）。スプリントコントラクトもスプリント構造の一部として廃止された。モデルがアップグレードしたらコントラクトの必要性を再評価すべき。
