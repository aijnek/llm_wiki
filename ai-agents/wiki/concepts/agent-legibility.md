# エージェントの認識可能性（Agent Legibility）

## 定義

AIエージェントがシステム・コードベース・アプリケーションの状態を直接認識・推論・検証できるように、情報やツールへのアクセスを整備すること。「エージェントがそれを読める・使える状態にあるか」という設計の観点。

## 背景

コードのスループットが増加するにつれて、人間がQAのボトルネックになる。人間の時間と注意力が固定された希少資源であるため、アプリケーションUI・ログ・メトリクスをエージェントが直接読み取れるようにすることで、エージェント自身がバグを再現・検証・修正できるようになる。

リポジトリが完全にエージェントによって生成されるため、まずエージェントの認識可能性が最優先で最適化される。「新規採用エンジニア向けにコードの操作性を向上させる」のと同じように、エージェントがリポジトリ自体からビジネスドメイン全体について推論できるようにすることが目標。

## 詳細

### アプリケーションの認識可能性

**Gitワークツリーごとのアプリ起動**
- 変更ごとに独立したアプリインスタンスを起動可能
- エージェントは変更前後の状態を独立した環境で検証できる

**Chrome DevTools Protocol連携**
- DOM スナップショット・スクリーンショット・ナビゲーションを扱うスキルを作成
- エージェントがバグを再現し、修正を検証し、UI動作を直接分析できる
- 修正前後の動画記録が可能

**監視機能（Observability）との統合**
- ログ・メトリクス・トレースをワークツリーごとの一時的なローカル監視スタックで公開
- エージェントがLogQL（ログ）・PromQL（メトリクス）でクエリ可能
- タスク完了後は破棄される（完全に隔離された環境）

### コードベースの認識可能性

**エージェント指向のアーキテクチャ設計**
- 「退屈な技術」（Boring Technology）を優先：構成可能性・APIの安定性・トレーニングデータでの表現でエージェントがモデル化しやすい
- 不透明な上流の挙動を持つライブラリより、エージェントが直接検査・変更できる内製実装を選択することがある
- 依存関係を明示的・検証可能な形態にする

**カスタムリンターのエラーメッセージ設計**
- リントエラーに修復手順を埋め込み、エージェントが自律的に修正できるようにする

### 認識可能性がもたらすプロンプトの可能性

認識可能性が整備されると、以下のような高レベルの指示が実現可能になる：
- 「サービスの起動を800ミリ秒以内に完了することを保証する」
- 「これら4つの重要なユーザージャーニーのいずれにおいても、どのスパンも2秒を超えない」
