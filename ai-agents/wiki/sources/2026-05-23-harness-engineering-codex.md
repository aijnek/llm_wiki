# ハーネスエンジニアリング：エージェントファーストの世界における Codex の活用

## 要点

- OpenAIのチームが5ヶ月間、手書きコード一切なしで約100万行のソフトウェアをCodexで構築・リリースした（3〜7人のエンジニア、約1,500 PR）
- エンジニアの役割が「コードを書く」から「環境設計・意図の明確化・フィードバックループ構築」へとシフトした（ハーネスエンジニアリング）
- AGENTS.mdは「百科事典」ではなく「目次」として扱うべき：巨大な指示ファイルはコンテキストを圧迫し逆効果
- エージェントの認識可能性（Legibility）を高める：アプリUI・ログ・メトリクスをCodexが直接読めるよう整備（Chrome DevTools Protocol連携、ローカル監視スタック）
- 厳格なアーキテクチャ不変条件をカスタムリンターで機械的に適用し、エージェント生成コードのドリフトを防止
- 定期実行のバックグラウンドエージェントによる「ガベージコレクション」でエントロピーを継続的に解消
- 単一プロンプトで設計→実装→テスト→レビュー→マージまでエージェントが完結できる段階に到達

## 詳細サマリー

OpenAIのエンジニアリングチームは2025年8月から、手書きコードを一切使わずにソフトウェア製品を構築するという実験を行った。5ヶ月後にはアプリケーションロジック・CI設定・ドキュメント・監視機能を含む約100万行のコードベースが完成し、社内で数百人のユーザーが日常的に利用している。わずか3名のエンジニアから始まり、エンジニア1人あたり1日平均3.5 PRのスループットを達成した。

この実験から生まれた概念が「ハーネスエンジニアリング」だ。エンジニアの主な仕事はコードを書くことではなく、エージェントが有用な作業を行えるよう環境・スキャフォールド・フィードバックループを設計することになった。タスクを深さ優先で分解し、エージェントが苦戦したときは「不足しているツールやガードレールは何か？」を問い続けることが重要となる。

コンテキスト管理はエージェントを大規模タスクで機能させるための最大の課題の一つだ。「1つの大きなAGENTS.md」アプローチは失敗した：コンテキスト圧迫・過度なガイダンスによる指針喪失・マニュアルの腐敗などが問題となった。代わりに、AGENTS.mdを約100行の「目次」として扱い、構造化されたdocs/ディレクトリを信頼できる情報源として整備する「段階的開示」アプローチが有効だった。リポジトリにバージョン管理されていない知識（Slackの議論など）はエージェントにとって存在しないも同然であり、すべての重要な意思決定はリポジトリにアーティファクトとして記録する必要がある。

アーキテクチャの一貫性はドキュメントだけでは保てない。カスタムリンターと構造テストによって依存関係の方向性や命名規則を機械的に強制し、エージェントが既存パターンを複製しても品質が劣化しないようにする。また、定期的に逸脱を検出してリファクタリングPRを作成するバックグラウンドエージェント（「ガベージコレクション」）が技術的負債の蓄積を防ぐ。
